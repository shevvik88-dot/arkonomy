# CLAUDE.md

Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.

## Known issues / tech debt
- **`sw.js`'s global fetch-listener catch-fallback returns a synthetic empty `Response('', {status:504})` for any failed/uncached GET request, regardless of resource type.** Added 2026-07-26 to fix `TypeError: Failed to convert value to 'Response'` (uncached URL + blocked/failed fetch previously resolved `event.respondWith()` to `undefined`) — correct for `<img>`/asset loads (a normal failed load, existing `onError` handlers degrade fine, e.g. `MerchantFavicon`). Not yet an issue in practice, but if app code ever calls `fetch()` on a non-excluded domain (the SW only excludes `supabase.co`/`finnhub.io`) expecting to parse JSON/text on failure, it would now get a 200-shaped-but-empty-body 504 instead of a rejected promise — worth adding that domain to the SW's exclusion list if/when such a caller is added, rather than relying on the synthetic Response being harmless by default.
- **Don't use a console-typed `throw new Error(...)` to test whether `window.onerror`/Sentry's global handler works.** DevTools Console REPL evaluates in its own VM context and doesn't reliably surface through `window.onerror` the same way a real runtime error does — this was the last of 5 stacked causes in the 2026-07-18 frontend Sentry investigation, and cost the most time since every other cause (missing DSN, missing release, CSP, stale tab) had already been fixed by the time it was found. To verify Sentry capture+transport end-to-end, call `Sentry.captureException(...)` directly (temporarily expose `window.Sentry = Sentry`, same disposable-hook pattern as everywhere else) or trigger a real error inside a React render/event handler — not a console-typed throw.
- **`_shared/recurringDetector.ts:211` computes `daysUntil` from the full `referenceDate` timestamp, not midnight** — `Math.round((nextDate.getTime() - referenceDate.getTime()) / MS_PER_DAY)` uses `referenceDate` as-is (e.g. "now" at whatever time the caller runs), while `nextDate` is already midnight-normalized. Same bug class already flagged in Coding rules ("always compare against midnight of today, not `new Date()`"). Found by code-reviewer during the `push-notify` migration (2026-07-17) — not introduced by that migration, inherited from the shared file (already live via `get-insights`). Currently safe: `push-notify`'s cron fires at 09:00, well under the ~12h rounding boundary where this could flip a day. Not fixed — would only matter if a cron schedule using this function's exact-day matching (`daysUntil === N`) ever moved to the afternoon/evening, where it could silently shift or drop that day's notification.
- **When integrating a new external service, verify keys/IDs line-by-line against the service's own dashboard FIRST — before hypothesizing complex technical causes.** The Sentry `arkonomy-edge-functions` integration cost ~2 hours of diagnosis (secret checks, code review, network tests) chasing a suspected SDK/Deno-version incompatibility, when the real cause was a copy-paste error at the second Sentry project's creation: `SENTRY_DSN` pointed at a different project ID than the one being watched in the dashboard. Sentry's ingest API returns 200 even for a wrong/nonexistent project ID (doesn't leak project existence), so `flush() === true` gave false confidence the whole time. Cheap credential/ID verification should come before expensive theories about SDK compatibility, network egress, or transport internals.

Not fixed today — needs `cleanMerchantName(s.name) || s.name` applied before it goes into `ctx`.
- **Health Score has no balance floor** — `calculateHealthScore()` (healthScore.js) only looks at income/spend trend across 4 components, never at actual cash position. Low-balance warning is a bolted-on `cashPositionLow` caption (Insights.jsx, Dashboard.jsx) next to the score, not a factor in the score/color/label itself.
- **`plaid_accounts` balance aggregation mixes `available`/`current` semantics** — `available` is often null for savings accounts at some banks and doesn't include pending the same way `current` does. Summing `available ?? current` per-row across multiple accounts of one user can blend the two semantics into one total. Fine for a single checking account; revisit before real multi-account/multi-bank aggregation.
- **`scheduled_payments` has no matching engine planned↔actual** — if the user doesn't mark a payment `completed` after the real Plaid transaction lands, `projectBalanceAt`/Cash Flow Forecast can double-count it (once as the pending scheduled payment, once as the real transaction). Deliberately not solved — matching by amount+date+description has a real false-positive/negative risk, separate task.
- **Level 2 calendar sheet shows only one dominant item per future day** — same single-item choice as the grid. If a day has both a recurring projection and a scheduled payment and the projection is larger, the scheduled payment (and its cancel button) is entirely hidden from the sheet until it becomes dominant. Not hit in current data (no overlapping days), so not fixed — would need the future-day sheet to show a list like past days already do (`selectedCatEntries`), not just one item.
- **Finnhub rate-limit ceiling is tighter than it looks** — `FINNHUB_API_KEY` is one shared key app-wide (60 req/min), and `market-data` has no batch-quote endpoint (one Finnhub call per ticker regardless of list size). A single Markets-home load costs 8 calls (trending+sectors) before watchlist; after raising the watchlist cap to 20 that's 28 calls/load — roughly 2 concurrent user loads before Finnhub starts 429ing part of the batch (was ~3 at the old cap of 12). Not a problem at current usage; will be a real ceiling as concurrent active users grow. Fix requires either a paid Finnhub tier or a server-side quote cache shared across users.

## Coding rules
- The normal Bearer access_token test pattern only works for functions that authenticate a regular user. For webhook (signature-verified, e.g. Stripe) or service_role-gated functions, don't try to reproduce or guess the real production secret (Stripe signing secret, `SUPABASE_SERVICE_ROLE_KEY`) — use the one-time `SENTRY_TEST_MARKER`-style pattern instead: generate a random secret, `supabase secrets set` it, check it against a dedicated header in a branch that runs BEFORE the real auth/signature check, then `secrets unset` + remove the code immediately after confirming in Sentry. Faster and safer than hunting for a real credential by hand (see `plaid-batch-sync` — three attempts to copy the real service role JWT from the Dashboard all had the wrong SHA256, never resolved that mismatch, and rotating `SUPABASE_SERVICE_ROLE_KEY` itself would have broken every function's DB admin access at once; the marker pattern from `stripe-webhook` would have been faster from the start).
- When a function's structure differs from an established pattern already applied elsewhere (no existing try/catch to hook into, a per-item catch that must stay untouched, a redirect-based handler instead of JSON responses, auth via signature/service-role instead of a normal user Bearer token) — describe the difference and the planned approach, then wait for explicit confirmation before writing code. Never silently force the new case into the previous pattern (see `delete-account`, `plaid-batch-sync`, `alpaca-oauth-callback` — each needed a distinct approach, caught by asking first).
- One step at a time — show the change, wait for confirmation before proceeding.
- Never rewrite large blocks when a targeted edit suffices.
- Never change auth flow, Supabase schema, or Vercel config without explicit instruction.
- Never add TypeScript, CSS modules, or new dependencies without asking first.
- Keep components in the file where they are used unless explicitly asked to extract.
- When editing a file, re-read it first; never rely on stale context.
- Never add a state variable (e.g. `user`) to a useEffect dependency array to fix a stale closure if that effect calls setState — use a ref instead (assign `ref.current = fn` inline after the function definition, call `ref.current()` inside the effect).
- When comparing a projected date against "today", always compare against midnight of today (`new Date(y, m, d)`), not `new Date()` — intraday timestamps cause same-day events to be treated as past.
- Before committing any new hook (`useState`/`useMemo`/`useEffect`/`useCallback`) in App.jsx, verify it sits above every early `return` in the component — a hook below an early return gets skipped on some renders and called on others, which crashes the whole app via a Rules of Hooks violation. App.jsx has broken production twice in two days from component-structure mistakes like this (a TDZ ordering bug, then this), not from feature logic — check structure, not just the diff, before pushing.
- Before writing any code that touches financial calculations or data already shown somewhere in the app (balances, recurring payments, health score, forecasts), search for existing logic first — grep for the concept, don't assume a fresh implementation is needed. This project has independently reimplemented the same calculation 4+ times: `plaid_accounts` derived-vs-real balance (pre-refactor), `recurringDetector.js` vs `recurringSummary.js` (two "is this recurring" engines, found 2026-07-12), `weekly-report/index.ts` hand-duplicating `healthScore.js`'s savings-points formula, and `_shared/recurringDetector.ts` (Deno) as a still-unfixed 4th copy. Each one silently disagreed with the others in a different, hard-to-notice way (wrong balance, wrong date, wrong subscription total) — this is a mandatory search step, not a one-time reminder.
- After deploying a visual change, if the user reports it's "not showing" in the live app, check the deployed bundle and git history before assuming a code regression — remind them to hard-refresh first. The Month Calendar's intensity scaling was correctly implemented and deployed since `bb0f116`, never removed; the user's "no variation visible" report on 2026-07-12 was the browser serving a cached bundle, confirmed by diffing the live JS against source before touching any code.
- For a multi-step task split into fix groups (e.g. a screen audit's "functional" vs "visual" groups), commit after EACH group before starting the next — never let two groups' changes sit uncommitted together in the working copy. A `code-reviewer` pass on group N sees the full working-tree diff, not just group N's changes; if group N-1 is still uncommitted, the reviewer can't tell what's actually in scope and may flag already-approved, already-deployed work as an undocumented change. Found 2026-07-18: Dashboard audit's functional group was deployed via `vercel --prod` straight from the working copy without an intermediate commit, so the visual group's review saw both groups mixed and flagged the (already-shipped) bankConnected gating as scope creep.
- Never use PostgREST embedded-select (`tableA.select('..., tableB(...)')`) between two tables unless a direct foreign key exists between exactly those two tables — PostgREST's auto-join needs a direct FK, not a transitive one through a third table, and fails with `PGRST200` otherwise. `notification_preferences.user_id` references `auth.users`, not `profiles` — `profiles.select('..., notification_preferences(...))')` silently broke every `weekly-report`/`generate-monthly-report` cron run (found 2026-07-25, fixed with two separate queries + a `user_id`-keyed `Map` merge in app code). Before writing an embedded-select against a new table, check its FK target first (`information_schema.table_constraints`/`key_column_usage`), especially for any table whose `user_id` might reference `auth.users` directly instead of `profiles`.
- When a function's `verify_jwt` platform setting looks inconsistent with sibling functions of the same kind (e.g. one cron-triggered function has `verify_jwt: true` while its siblings all have `false`), that's a real bug to investigate, not a stylistic quirk — the gateway rejects non-JWT-shaped tokens (like a rotated `sb_secret_...` service key) before the function's own code ever runs, silently blocking legitimate service-role callers. Fixing it is a redeploy with/without `--no-verify-jwt`, not a code change — safe as long as the function already does its own `token === Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')`-style check internally (confirm this exists before flipping the flag).

## Security decisions — DO NOT CHANGE without explicit instruction
- **plaid_items has NO SELECT RLS policy** — intentional. Removed during security audit to prevent `access_token` from being exposed to the client. Never add a SELECT policy back.
- **checkBankConnection() calls `check-bank-connection` edge function** (supabase/functions/check-bank-connection/) — uses service role key server-side, returns `{ connected, institution_name, count, error_code }`. Never revert to direct `.from("plaid_items").select()` in the frontend.
- **App Check verification uses JWKS (not the verifyToken REST API)** — the REST API requires a Google service account OAuth token; without credentials it returns 403 and would block all requests. JWKS fetches Google's public keys and verifies the RS256 JWT directly. Never switch to the REST API approach.
- **App Check bypasses for service-role paths** — `resync_all`, `sync_item` (plaid-sync-transactions), and cron calls (weekly-report) skip App Check because they originate server-side with no browser context. The outer `if (ENVIRONMENT !== 'development')` guard is intentional; verifyAppCheck itself has no dev bypass so the guard must live at each call site.
- **Plaid env vars** — Production approval in progress; do not touch.
- **usePlan.js** — Free/Pro gating is core business logic; never bypass.
- **`profiles.alpaca_access_token`/`alpaca_refresh_token` must never be SELECTed client-side** — same class of decision as `plaid_items.access_token`. Client checks Alpaca-connected status via the `has_alpaca_token()` RPC (no `SECURITY DEFINER`, no parameters, runs under `profiles_owner_select` RLS) instead. Never add these columns back to `App.jsx`'s `profiles` select list.
- **`check_and_increment_rate_limit` (and any future `SECURITY DEFINER` RPC) must `REVOKE EXECUTE FROM PUBLIC, anon, authenticated` and `GRANT` only to `service_role`** — a `SECURITY DEFINER` function bypasses RLS by design; leaving it at Postgres's default PUBLIC execute grant lets any authenticated client call it directly via PostgREST with attacker-chosen arguments. Follow the `login_attempts.sql` pattern for any new one.
